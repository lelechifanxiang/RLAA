# tracing 修改意见 0601

## 审阅范围

本次只审阅当前 tracing 子包及其紧邻依赖，重点查看以下几类风险：

- 公开接口和真实行为是否一致
- 是否存在静默算错而不是显式失败的路径
- 是否违背当前项目的 batch-first、tensor-first、GPU-first 约定
- 现有测试是否真的覆盖了默认 tracer 的真实行为

涉及的主要文件：

- optics_core/tracing/_core.py
- optics_core/tracing/_dispatch.py
- optics_core/tracing/_hits.py
- optics_core/tracing/_interactions.py
- optics_core/tracing/_sampled_rays.py
- optics_core/first_order.py
- optics_core/geometries.py
- optics_core/surfaces.py
- optics_core/rays.py

## 高优先级问题

### 1. EvenAsphere 的非空 coefficients 会被静默忽略

现状：

- optics_core/geometries.py:197 的 EvenAsphereGeometry 只是继承 StandardGeometry 并多了一个 coefficients 字段，没有覆盖 sag、normal、intersect。
- optics_core/surfaces.py:98 允许用户正常创建带 coefficients 的 EvenAsphereSurface。
- optics_core/tracing/_dispatch.py 会把 EvenAsphereSurface 直接送入和球面共用的 sag kernel。
- tests/contract/test_surface_trace_kernels.py:69 只验证了 coefficients 为空时与球面共核，没覆盖非空 coefficients。

风险：

- 这不是“暂未支持然后报错”，而是“接受输入但按球面计算”，属于静默错误。
- 一旦用户传入真实非球面系数，结果会看起来正常，但数值物理意义不对，后续很难排查。

建议：

1. 在真正实现 EvenAsphereGeometry 之前，先在构造或 dispatch 阶段对非空 coefficients 显式报错，避免 silent wrong result。
2. 实现后再补 sag、normal、intersect 的 Zemax 对标测试，至少覆盖单系数、混合系数和边缘孔径三个场景。

### 2. CoordinateBreak 仍是公开 surface 类型，但默认 tracer 直接失败

现状：

- optics_core/surfaces.py:141 定义了 CoordinateBreak，并且 SurfaceSequence 提供 add_coordinate_break。
- optics_core/tracing/_dispatch.py:49 遇到 CoordinateBreak 时直接抛 NotImplementedError。
- tests/support.py:8 定义了 ShowcaseSmokeTracer，tests/support.py:96 让 showcase 系统使用 smoke tracer 而不是 SequentialSurfaceRayTracer。

风险：

- 对外暴露了 API，也出现在 showcase 拓扑里，但默认 tracer 仍然不可用。
- 当前测试把这个缺口绕过去了，所以后续很容易误以为“CoordinateBreak 已经能跑完整链路”。

建议：

1. 如果短期内不实现真实 frame transform，就在系统构建或 trace 入口更早失败，并在文档中明确声明不支持 CoordinateBreak。
2. 如果要实现，建议先做最小版本：只支持平移和绕 z 轴旋转，再逐步补全完整 frame 变换。
3. CoordinateBreak 一旦落地，必须新增基于真实 SequentialSurfaceRayTracer 的回归测试，不能再用 smoke tracer 代替。

### 3. tracing 主链仍不满足 GPU/device 契约

现状：

- optics_core/first_order.py:29 的 surface_value 和 optics_core/first_order.py:88 的 surface_position 都直接返回 CPU FP64 tensor。
- optics_core/tracing/_hits.py:24 和 optics_core/tracing/_dispatch.py:112 直接把这些查询结果送入 tracing 主链，没有对 device 做对齐。
- optics_core/tracing/_sampled_rays.py:77 和 optics_core/tracing/_sampled_rays.py:78 在主路径里把 tensor detach 后搬回 CPU 再转 list 写入 metadata。

风险：

- 一旦 RayBundle 在 CUDA 上，当前代码会出现 device mismatch，或者被迫做额外 host-device 同步。
- 这和项目当前“GPU 加速、多系统并行、避免 CPU-GPU 往返”的方向直接冲突。

建议：

1. first_order 查询函数新增参考 device 或 reference tensor 参数，返回结果和调用侧 tensor 保持相同 device。
2. tracing 内部统一采用“由输入 ray tensor 决定 device”的策略，不要在热路径里创建裸 CPU tensor。
3. metadata 中不要默认保存大 tensor 的 cpu().tolist() 结果，改成按需开启，或只保存轻量摘要。
4. 新增一个 CUDA 可用时才执行的 contract/regression 测试，至少覆盖 plane hit、paraxial hit 和一次 refract。

### 4. Surface aperture 和 field vignetting 还没有进入 valid 语义

现状：

- optics_core/surfaces.py:35 定义了 aperture_radius。
- optics_core/first_order.py:55 已经有 stop_aperture_radius，这说明系统层已经承认 aperture 是正式概念。
- 但 tracing 主链的有效性判断目前只有 optics_core/tracing/_core.py:131 开始的 isfinite 检查。
- 当前 tracing 子包里没有任何 surface aperture 或 field vignetting 裁剪逻辑。

风险：

- 光线只要能和几何面求交，就会继续被视为 valid，即使已经落在物理孔径之外。
- 这会让 spot、chief ray、透过率和 Zemax 对标结果系统性偏乐观，而且属于静默偏差。

建议：

1. 在每个 surface hit 后增加 clear-aperture 检查，把超孔径光线从 valid 中裁掉。
2. 如果后续要接入 field vignetting，建议沿用同一个 hit.valid 机制，而不是额外再造一套 mask。
3. SurfaceIntersection 需要考虑补一个 valid 或 clipped 标记，否则下游只能靠 NaN 猜测是否命中有效孔径。

## 中优先级问题

### 5. TraceOptions 和 TraceResult 有公开字段，但默认 tracer 没有兑现

现状：

- optics_core/rays.py:42 到 45 暴露了 record_intersections、record_opd、record_ray_angles、warm_start。
- optics_core/rays.py:60 到 61 暴露了 ray_angles_in_deg 和 ray_angles_out_deg。
- 真实的 SequentialSurfaceRayTracer 只处理 intersections，当前没有填充 OPD、ray angles，也没有使用 warm_start。
- tests/regression/test_demo_pipeline_regression.py:37 会把 record_ray_angles 传进 trace，但该回归跑的是 tests/support.py 里的 smoke tracer，不是默认实现。

风险：

- 调用方看到 API 会自然认为这些开关有效，但默认 tracer 实际忽略了它们。
- 这会导致接口文档、测试和真实行为三者继续漂移。

建议：

1. 短期内优先收口公开 API：未实现的字段先移除、标记为保留、或在 trace 入口显式报 NotImplementedError。
2. 如果要保留字段名，就必须补一条真实 tracer 的回归测试，避免以后继续只靠 smoke tracer 过关。

### 6. intersection 快照的默认策略对大 batch 不友好

现状：

- optics_core/rays.py:42 让 record_intersections 默认为 True。
- optics_core/tracing/_core.py:108 每个 surface 都会把 intersections 列表一路往下传。
- optics_core/tracing/_hits.py:127 到 131 对 normal 和 position 全量 clone 后再写入 SurfaceIntersection。

风险：

- 当前 batch 维是 design x field x wavelength x ray，若 surface 数再上去，交点快照会把显存或内存放大到 surface_count 倍。
- 这和 tracing 作为大规模并行主链的用途不匹配，默认配置过重。

建议：

1. 把 record_intersections 的默认值改成 False，更符合“只在调试和分析时开启”的定位。
2. 如果业务上经常需要交点，建议增加轻量模式，例如只记录 position、不记录 normal，或只记录指定 surface。
3. 后续如果实现 aperture clipping，最好不要再用 clone + NaN 作为唯一状态表达方式。

## 建议补充测试

### 必补的正确性测试

1. 非空 EvenAsphere coefficients 必须要么显式报错，要么与 Zemax 数值对齐。
2. CoordinateBreak 使用真实 SequentialSurfaceRayTracer 的最小回归，至少覆盖一段平移或旋转后仍能对上像面位置。
3. aperture clipping 回归，验证超出 clear aperture 的光线会被标记为 invalid。
4. record_ray_angles、record_opd、warm_start 的真实行为测试，禁止再只由 smoke tracer 覆盖。

### 必补的工程性测试

1. CUDA 可用时的 device 回归，确保 first_order 查询和 tracing 主链不会混入 CPU tensor。
2. 大 batch + 多 surface 的内存烟雾测试，防止 intersections 默认策略把内存放大到不可控。

## 建议的实施顺序

建议不要同时铺开太多功能，优先按下面顺序收敛风险：

1. 先补 fail-fast：禁止非空 asphere coefficients 的静默降级，明确 CoordinateBreak 和未兑现 TraceOptions 的行为。
2. 再补物理正确性：surface aperture clipping，并同步完善 valid/intersection 语义。
3. 再补 device 契约：把 first_order 和 sampled_rays 的 CPU 路径改成 device-aware。
4. 最后做性能收口：调整 intersections 默认策略，减少 clone 和 cpu().tolist()。

## 结论

当前 tracing 子包的结构已经比之前清晰很多，但仍然存在几类高风险空洞：

- 对外暴露了功能，但默认 tracer 还不能跑
- 接受了输入，但会静默按更弱模型计算
- API 字段已经公开，但真实实现并未兑现
- 和 GPU/batch-first 目标仍有明显摩擦

下一轮如果只做一件事，我建议优先处理“静默算错”和“公开功能不可用”这两类问题，也就是 EvenAsphere 非空系数和 CoordinateBreak。
