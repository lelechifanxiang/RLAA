# 波长与材料执行态索引化方案

## 1. 结论

本项目以大批量并行追迹为主要目标，波长集合和材料集合应当在 `system.prepare()` 阶段一次性确定并编译。进入追迹热路径后，不再接收任意物理波长，也不再从波长值反查索引，而是只使用系统级波长索引访问预计算折射率表。

建议采用下面的数据关系：

```text
system.wavelengths
        │ prepare()
        ▼
system.wavelengths: value、weight、primary_index
        │
        ├── prepare() ──► wavelength_um[W]、refractive_index_table[M, W]
        │
        └── 生成光线 ──► wavelength_index（全局波长索引）
                              │
                              ▼
                   table[material_index, wavelength_index]
```

这里的 `W` 是系统的固定波长数，`M` 是整个异构 batch 中去重后的材料数。

## 2. 当前实现的问题

目前 `RayBundle` 保存每根光线的 `wavelength_um`。追迹开始时，系统需要把这些浮点值重新映射到材料折射率表的列号：

```python
difference = torch.abs(wavelength.unsqueeze(-1) - material_data.wavelength_um)
wavelength_index = torch.min(difference, dim=-1).indices
```

这会带来三个问题：

1. 系统刚刚用自己的波长列表构建材料表，追迹时又从浮点值恢复同一个索引。
2. 匹配产生 `光线数量 × 波长数量` 的临时 tensor，不适合大批量追迹。
3. `RayBundle` 在逻辑上为每根光线携带 FP64 波长值，但同一波长批次通常只来自少量固定波长。标准构造中的 `expand` 视图不一定实际分配完整波长 tensor，因此主要显存问题仍是前述匹配临时量。

当前实现允许手工构造任意波长光线，因此映射在现有接口下是必要的；但这项灵活性与本项目的主要使用方式不一致，可以主动收紧。

## 3. 建议的数据模型

### 3.1 系统准备态

准备阶段直接生成只读的材料执行态，不再额外增加一层波长对象：

```python
BatchedMaterialData
    material_index: Tensor[D, S]      # int64
    wavelength_um: Tensor[W]          # FP64
    wavelength_weights: Tensor[W]     # FP64
    refractive_index_table: Tensor[M, W]  # FP64
```

其中：

- `D`：异构镜头数量。
- `S`：表面数量。
- `material_index[d, s]`：第 `d` 个镜头在第 `s` 个面后的材料编号。
- `refractive_index_table[m, w]`：材料 `m` 在系统波长 `w` 下的折射率。

材料名称解析、材料去重和色散公式计算只在准备阶段执行一次。

### 3.2 光线数据

`RayBundle` 不再保存 `wavelength_um`，改为保存：

```python
wavelength_index: torch.Tensor  # int64，可广播到光线 batch shape
```

标准追迹的光线形状仍为：

```text
[design, field, selected_wavelength, ray]
```

`selected_wavelength` 是本次选择的局部轴，而 `wavelength_index` 保存其在 `system.wavelengths` 中的全局编号。例如只追迹系统第 2 个波长时，局部波长轴长度为 1，但其中的索引值仍为 2。

索引 tensor 可以使用 `reshape + expand` 构造广播视图，不需要为每根光线分配一份完整数据。

### 3.3 物理波长的使用

需要物理波长的计算通过准备态查询：

```python
wavelength_um = material_data.wavelength_um[wavelength_index]
```

追迹中的折射、光程累积只需使用材料表索引；波前、PSF 等确实需要波长值的模块再执行上述查询。不要在 `RayBundle` 中同时保存波长值和索引，否则会产生两份可能不一致的状态。

## 4. 接口与生命周期变化

建议收紧以下契约：

1. `MultiOpticalSystem` 必须先声明至少一个波长，再调用 `prepare()`。
2. `prepare()` 一次性编译波长表、材料索引和折射率表，并将它们放到目标 device。
3. 正式追迹要求系统已经准备完成，不再在 `_trace_surfaces()` 中按需编译材料。
4. `build_pupil_rays()` 接收 `wavelength_indices`，不再接收任意 `wavelength_um`。
5. 一阶 probe 光线直接使用 `system.wavelengths.primary_index`。
6. 手工构造的 `RayBundle` 也只能引用系统已有波长索引；不再支持临时定义新波长。

追迹热路径可以因此简化为：

```python
material_data = system._material_data
incident_index = material_data.refractive_index_table[
    incident_material,
    rays.wavelength_index,
]
```

不再需要 `_material_context_for()`、浮点波长比较或追迹期间的材料表重建。

如果系统的波长或材料选择发生变化，应重新执行 `prepare()`；曲率、厚度等不影响材料执行态的连续参数变化，可以由后续的参数执行态更新机制单独处理。

## 5. 收益与代价

主要收益：

- 删除每次追迹前的波长匹配和临时差值 tensor。
- 折射率表在 GPU 上一次生成、反复复用。
- 光线只携带 int64 索引广播视图，材料热路径不再依赖重复的物理波长值。
- 单波长、波长子集和全波长追迹共享同一套全局索引语义。
- 不存在浮点容差匹配和材料缓存被隐式重建的问题。

主要代价是一次有意的接口破坏：现有手工 `RayBundle(wavelength_um=...)`、测试夹具和 Zemax 辅助代码需要统一改为波长索引。考虑到项目尚在快速重构阶段，并且性能目标明确，这项代价是可接受的。

## 6. 推荐实施边界

本次重构只需要完成波长与材料执行态的索引化，不必同时引入庞大的 `TraceRuntime`：

1. 让 `BatchedMaterialData` 严格使用系统波长顺序构建 `[M, W]` 表，不再对波长排序或去重。
2. 将 `RayBundle.wavelength_um` 替换为 `wavelength_index`。
3. 修改采样光线、probe 光线和分析模块，在需要时从材料执行态查询物理波长。
4. 删除追迹热路径中的波长解析和材料按需编译分支。

完成后再通过 GPU benchmark 分别记录准备耗时、追迹耗时和峰值显存，确认收益来自热路径简化，而不是把开销转移到每个 batch 的其他位置。
