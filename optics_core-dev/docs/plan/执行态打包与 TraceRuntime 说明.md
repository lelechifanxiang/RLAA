# 执行态打包与 TraceRuntime 说明

## 1. 目的

这份文档用于说明一个容易在接口设计阶段被混淆的问题：

1. 公开接口应该如何保持清晰、稳定、可扩展。
2. GPU 并行追迹和像质评估的热路径应该如何避免被高层封装拖慢。
3. “OpticalSystem 等公开对象”和“GPU 执行时真正消费的数据”之间应该如何分层。

核心结论是：

公开接口可以保持面向对象和分层设计，但真正进入 tracing 和 evaluation 热路径的数据，最好在执行前先整理成专用的执行态对象，而不是在每次追迹时沿着 Python 对象图逐层读取。

## 2. 什么是“系统冻结后编译成执行态”

这里的“冻结”和“编译”都不是狭义的编译器概念，而是工程上的执行准备。

### 2.1 系统冻结

“系统冻结”指的是：

在一次 trace、一次 merit 评估、一次分析任务，或者一个优化内层循环里，把当前系统视为暂时不变的输入。

典型冻结内容包括：

1. 面序列及其类型。
2. stop 面位置。
3. 材料模型种类。
4. 非球面系数槽位数量。
5. 坐标间断结构。

一旦这些结构信息稳定下来，就不应该在每次 trace 时重新解释和组织。

### 2.2 编译

这里的“编译”更接近下面三个动作：

1. lowering：把高层对象图降成规则、扁平、适合批量计算的结构。
2. packing：把 GPU 高频访问的数据整理为连续 tensor 或 buffer。
3. specialization：根据当前系统结构固定 shape、dtype、device、缓存布局和类型编码。

因此，这里的编译不是指一定要生成 CUDA 代码，而是把“可读的系统描述”转成“可高效执行的运行时快照”。

### 2.3 执行态对象

执行态对象可以命名为 PackedOpticalSystem、TraceRuntime 或类似名字。它的职责不是对外暴露 API，而是给 tracing、ray aiming、evaluation 内核提供高频访问的数据底座。

## 3. 这不等于“所有接口都直接操作全局 tensor”

这个方向最容易产生的误解是：

是不是应该把整个系统做成一个巨大的全局 tensor，然后让所有模块直接围绕这个 tensor 写接口。

更准确的理解是：

1. 公开层仍然使用 OpticalSystem、Surface、Geometry、Material、PupilSampler、RayAimer 这类对象表达业务语义。
2. 只有进入 tracing、aiming、evaluation 热路径之前，才把这些对象编译成执行态。
3. 热路径直接消费执行态中的连续数据，而不是反复访问 Python 对象树。

也就是说，外部接口不需要直接暴露这些底层 tensor；它们应当被封装在执行态对象内部，由 tracer 和 evaluator 使用。

## 4. 为什么需要这层执行态

GPU 并行效率通常不会被“模块数量多”拖慢，而会被下面这些问题拖慢：

1. 在热路径里逐层访问 Python 对象。
2. 每个 surface 都做动态类型判断。
3. 每次 trace 都重新解析材料、坐标、采样模板。
4. 高频路径里重复创建小 tensor。
5. host 和 device 之间频繁搬运数据。
6. 本可复用的中间数据没有缓存。

因此，执行态的目标不是美化架构，而是把解释性工作从热路径移出去。

## 5. 执行态里通常放什么

执行态不必是一个巨大总 tensor，更合理的做法通常是“一组按语义分开的连续 buffer”。

典型内容包括：

1. surface 类型编码。
2. interaction 类型编码。
3. stop mask。
4. 曲率、锥常数、厚度、口径半径。
5. 非球面系数矩阵。
6. 坐标变换矩阵或其紧凑表示。
7. 材料索引表。
8. 材料色散系数或预计算折射率表。
9. 波长表与权重。
10. 视场表与相关采样配置。

如果未来支持图像仿真，还可以进一步保留：

1. pupil sampling 权重。
2. chief ray 相关缓存。
3. opd 累积路径。
4. sensor plane 几何信息。

## 6. 为什么通常不建议把它做成“一个总 tensor”

从实现上看，系统数据天然是异构的：

1. 有 float 参数。
2. 有 int 类型编码。
3. 有 bool mask。
4. 有变长非球面系数。
5. 有只读参数和可更新状态。

强行塞成一个总 tensor 往往会导致：

1. dtype 混乱。
2. padding 过多。
3. 更新粒度变粗。
4. 代码可读性下降。

因此更合理的实现通常是：

1. 若干个规则化的参数 tensor。
2. 少量类型编码 tensor。
3. 若干缓存对象或 cache 字典。

## 7. 对 auto_od 更合适的拆法

对于当前项目，更建议把“执行态”拆成三层，而不是只有一个对象。

### 7.1 PackedTopology

用于存放低频变化的信息：

1. 面序列及 surface type code。
2. stop 面位置。
3. 参数槽位布局。
4. 材料模型类型。
5. 坐标间断结构。
6. 哪些面允许非球面，哪些参数可优化。

这些信息只有在拓扑变化时才需要重建。

### 7.2 BatchedLensState

用于存放高频变化、适合批量更新的信息：

1. 曲率张量。
2. 厚度张量。
3. 材料选择索引。
4. 非球面系数张量。
5. 其他随候选镜头批量变化的连续参数。

对于 auto_od 这种多候选镜头并行求值场景，这一层尤其重要，因为它允许在不重建拓扑的情况下频繁更新参数批次。

### 7.3 TraceRuntime

用于组合真正执行时需要的内容：

1. PackedTopology。
2. 当前 BatchedLensState。
3. 采样模板缓存。
4. 材料折射率缓存。
5. warm start 缓存。
6. tracing 和 evaluation 共享的中间结果缓存。

## 8. 什么时候需要重编译，什么时候只更新状态

建议明确区分两类变化。

### 8.1 需要重编译的情况

1. 增删面。
2. 改 surface 类型。
3. 改 stop 面位置。
4. 改材料模型种类。
5. 改非球面槽位数。
6. 改坐标间断结构。

### 8.2 只需要更新 BatchedLensState 的情况

1. 曲率数值变化。
2. 厚度数值变化。
3. 材料在已知材料集合里切换索引。
4. 非球面系数数值变化。
5. 同一拓扑下不同候选镜头的批量参数变化。

这个区分的价值在于：

避免每轮 merit 评估都重新构建整套执行态，从而抵消掉执行态带来的性能收益。

## 9. 它和当前接口定义的关系

当前接口定义的主要目标是“冻结公开 API”，而不是在阶段 1 就完成高性能实现。

因此，一个合理的关系应该是：

1. OpticalSystem 是公开入口。
2. SurfaceSequence、MaterialLibrary、PupilSampler、RayAimer 等对象负责表达系统和调用语义。
3. SequentialSurfaceRayTracer 内部再决定如何把系统编译成执行态。

换句话说：

公开 API 不需要直接暴露 PackedTopology、BatchedLensState、TraceRuntime；但接口文档应当明确，后续实现层可以采用这种执行态设计，以避免公开层抽象进入热路径。

## 10. 这些内容属于哪个阶段

这部分内容既和阶段 1 有关，也和阶段 5 有关，但两者关注点不同。

### 10.1 属于阶段 1 的部分

阶段 1 需要考虑的是“设计约束”和“接口边界”，而不是具体优化落地。

阶段 1 应当至少明确下面几点：

1. 公开接口层和执行层是分离的。
2. tracing 和 evaluation 的热路径不应直接依赖高层对象图逐层解释。
3. 后续实现允许在内部引入 PackedOpticalSystem 或 TraceRuntime 一类执行态。
4. 拓扑信息和高频变化参数最好分开建模。
5. 未来缓存、warm start、材料折射率表、采样模板等优化，都应有清晰挂载位置。

这些属于阶段 1 的“架构前提”。如果阶段 1 完全不考虑这些问题，后面阶段 5 往往会被接口边界反向限制。

### 10.2 属于阶段 5 的部分

阶段 5 才是把这些思路真正做成性能收益的阶段。

阶段 5 关注的内容包括：

1. 执行态真实字段怎么组织。
2. 哪些 tensor 常驻 device。
3. 材料折射率表怎么缓存。
4. 采样模板怎么缓存。
5. warm start 如何复用。
6. 是否引入 mixed precision。
7. 是否评估 torch.compile、CUDA Graph、Triton 或更底层 fused kernel。
8. benchmark 如何量化加速收益。

因此，阶段 1 是“把门留出来”，阶段 5 是“真正把性能做出来”。

## 11. 当前处于阶段 1，做到什么程度算足够

对于当前阶段，接口定义做到下面这些，通常就已经足够：

1. 明确公开主入口和对象关系。
2. 明确 batched trace、sampling、analysis 的对外调用方式。
3. 明确结果对象、shape、dtype、device 的契约。
4. 明确 tracing 层是可替换实现，而不是把实现细节写死在公开接口里。
5. 在文档层明确“实现层可在内部编译执行态，公开 API 不等于热路径表示”。

换句话说，阶段 1 不需要现在就实现 PackedTopology、BatchedLensState、TraceRuntime，也不需要现在就决定最终 tensor 布局。

但阶段 1 最好至少写清楚一个原则：

高层 API 负责可读性和稳定性，执行层负责高频求值效率，二者应当分离。

## 12. 对当前文档状态的判断

如果只问“当前接口定义是否已经可以作为阶段 1 的主体交付”，答案是：基本可以。

当前接口文档已经完成了下面几件关键事情：

1. 固定了 OpticalSystem 作为公开主入口。
2. 固定了 surfaces、fields、wavelengths、materials、analysis、tracer 的对象关系。
3. 明确了 batched trace 作为公开主入口。
4. 把采样、瞄准、追迹、分析从职责上拆开。

这已经足以支撑阶段 1 的主目标。

但如果要让后续阶段 3 到阶段 5 更顺，建议在阶段 1 文档范围内再补一句或一小节原则说明：

1. 公开对象图不代表热路径内部表示。
2. 后续 tracer 实现允许把系统编译成执行态。
3. 拓扑和高频参数建议分离。

这个补充属于“阶段 1 的设计边界澄清”，不属于“阶段 5 的性能实现工作”。

## 13. 一句总结

执行态打包不是要推翻当前接口定义，而是要保护当前接口定义。

它的作用是：

1. 让公开 API 继续保持清晰。
2. 让 tracing 和 evaluation 的热路径不被 Python 对象层次拖慢。
3. 为阶段 5 的缓存、warm start、编译优化和性能调优预留稳定落点。

因此，在当前阶段，接口定义本身基本已经够用；但最好在文档里明确“公开接口层”和“执行态层”是两层不同的东西。
