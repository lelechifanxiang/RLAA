# 分工方案

## 1. 结论先行

针对当前项目背景，最合理的分工不是平均分配，而是按“算法语义 ownership”和“软件工程 ownership”分开。

建议角色定位如下：

1.  A 算法语义负责人，也是 tracing 和 evaluation 的最终正确性 owner。
    
2.  B 项目技术负责人，负责接口设计、工程拆分、测试体系、benchmark 框架和整体推进。
    
3.  C 独立光学 reviewer 和跨项目泛化负责人，负责第二视角校验、zoom 场景约束输入、外部 benchmark 设计。
    

一句话概括：

*   A 管“算得对不对”
    
*   B 管“怎么拆、怎么测、怎么落地”
    
*   C 管“能不能泛化到别的项目，以及外部怎么对标”
    

## 2. 为什么这样分工

当前三个人的能力结构并不对称，反而适合形成一个稳定三角：

1.  A 对现有代码和算法细节最熟 这是 tracing、入瞳估计、像质评价正确性的关键来源。
    
2.  B 软件工程能力最强，且熟悉 wrapper 和调用方式 更适合主导接口、模块边界、测试和演进节奏。
    
3.  C 熟悉另一套变焦自动设计项目，也熟悉光线追迹原理 很适合充当“第二算法视角”和“跨项目复用约束输入方”。
    

因此，最不推荐的方式是：

*   让 A 单独主导整个基础库重构
    
*   让 B 单独决定算法语义
    
*   让 C 只做外围支援不参与关键设计
    

那样会分别带来：

*   架构质量不稳定
    
*   语义偏差风险高
    
*   跨项目泛化不足
    

## 3. 角色定位

## 3.1 A 的角色

建议定位：算法语义 owner。

主要职责：

1.  明确当前 tracing 和 evaluation 的真实语义。
    
2.  指出哪些行为是“必须保持”的，哪些是历史实现细节。
    
3.  审核接口剥离后数值行为是否仍然正确。
    
4.  主导分析追迹和像质评价的性能热点是否可安全优化。
    

不建议 A 作为主要 owner 的内容：

*   包结构设计
    
*   测试框架搭建
    
*   benchmark 自动化脚本
    
*   CI 或文档体系
    

原因不是 A 不重要，而是这些工作不是 A 的比较优势。

## 3.2 B 的角色

建议定位：技术负责人兼工程 owner。

主要职责：

1.  主导 optics\_core 的接口设计和模块边界划分。
    
2.  负责从现有项目到新基础库的适配路线。
    
3.  负责回归测试、接口契约测试、性能 benchmark 的框架搭建。
    
4.  负责里程碑推进、风险收敛和最终交付组织。
    

B 最适合做的事情：

*   把 A 的隐式知识固化成接口和测试
    
*   把 C 的跨项目诉求变成明确需求
    
*   防止重构过程变成“只靠口头记忆维护的代码迁移”
    

## 3.3 C 的角色

建议定位：独立 optical reviewer 和泛化 owner。

主要职责：

1.  从另一个自动设计项目视角审视接口是否足够通用。
    
2.  补充 zoom 系统、跨项目调用、图像仿真的未来约束。
    
3.  参与 benchmark case 设计，特别是与 Zemax API 和 Optiland 的对标。
    
4.  对 tracing/evaluation 的数值输出做第二轮独立光学审查。
    

这部分很重要，因为如果只有 A 和 B，很容易得到一个“只适配当前项目”的库，而不是一个真正能复用的基础库。

## 4. 建议的职责边界

建议把整个工作拆成 6 个工作包，每个工作包明确 owner、support 和 reviewer。

| 工作包 | 内容 | Owner | Support | Reviewer |
| --- | --- | --- | --- | --- |
| WP1 | 基础库边界定义 | B | A, C | A, C |
| WP2 | 接口与模块设计 | B | A, C | A, C |
| WP3 | 基线测试与 benchmark 框架 | B | C | A |
| WP4 | 第一次接口剥离 | B | A | C |
| WP5 | 外部 benchmark 与结果解释 | C | B | A |
| WP6 | 并行优化与性能提速 | A | B | C |

其中最关键的决策权建议如下：

1.  算法语义最终解释权 A
    
2.  接口与包结构最终解释权 B
    
3.  跨项目泛化和未来扩展要求最终解释权 C
    

## 5. 分阶段分工建议

## 5.1 阶段 0：边界确认与现状冻结

目标：

明确哪些内容属于 optics\_core，哪些保留在 algorithms 层。

建议分工：

1.  A列出现有 tracing、evaluation 中必须保持的行为清单。
    
2.  B负责整理边界文档，把行为清单转换成待迁移模块清单。
    
3.  C从 zoom 项目视角补充“未来必须支持的场景”和“不应被当前单项目写死的假设”。
    

这一阶段的交付建议由 B 汇总，A 和 C 审核。

## 5.2 阶段 1：接口定义

目标：

定义 system、sampling、tracing、evaluation、imaging 的初步接口。

建议分工：

1.  B主导 dataclass、函数签名、模块目录、输入输出 shape 约定。
    
2.  A审核接口是否丢失必要光学语义，特别是 tracing 和 evaluation 所需的隐藏状态。
    
3.  C审核接口是否能支持 zoom 项目、后续图像仿真和更一般的 optical system。
    

这一阶段推荐由 B 起草接口文档，A 和 C 只对“是否足够正确和足够通用”提审查意见，不建议三个人同时改接口文案。

## 5.3 阶段 2：测试基线建立

目标：

在正式剥离前，先把现有行为冻结下来。

建议分工：

1.  B主导测试框架，建立 regression test、contract test、benchmark test 三类测试。
    
2.  A提供 3 到 5 个现有系统作为基线样例，并定义哪些指标必须严格对齐。
    
3.  C增加 1 到 2 个更偏 zoom 或更一般化的测试样例，防止样例过度贴合当前项目。
    

这一阶段不建议 A 写测试 harness，也不建议 C 单独写 benchmark 自动化。框架性工作由 B 统一完成，A 和 C 提供样例与判断标准。

## 5.4 阶段 3：第一次接口剥离

目标：

把 tracing 和 evaluation 核心能力从当前 DiffLensPopulation 中剥出来，同时保持旧项目能继续运行。

建议分工：

1.  B主导目录搭建、适配层和分步迁移顺序。
    
2.  A参与 geometry、materials、tracing、evaluation 核心实现的迁移或逐段审查。
    
3.  C负责独立调用新接口做验证，检查是否存在“接口上能用，但跨项目不顺手”的问题。
    

建议第一次剥离顺序：

1.  geometry 和 materials
    
2.  tracing
    
3.  sampling
    
4.  evaluation
    

这里的关键点是：

*   B 负责让结构可维护
    
*   A 负责让语义不跑偏
    
*   C 负责让接口不过度绑定当前项目
    

## 5.5 阶段 4：外部 benchmark 建立

目标：

建立当前项目、新基础库、外部参考工具之间的对标体系。

这一阶段建议 C 作为 owner，因为它最适合承担“独立于当前代码习惯之外的验证视角”。

建议分工：

1.  C主导 benchmark case 设计和对比维度定义。
    
2.  B 负责 benchmark harness 自动化和结果汇总脚本。
    
3.  A 负责解释 benchmark 差异背后的光学语义原因，判断是 bug、模型差异还是数值容差问题。
    

## 5.6 阶段 5：并行优化与性能加速

目标：

在接口稳定后，对 tracing 和 evaluation 做可量化的性能优化。

这一阶段建议 A 作为 owner，因为它最了解哪些计算路径可以改、哪些不能轻易动。

建议分工：

1.  A 主导热点识别与数值安全边界判断，特别是 tracing、Newton 迭代、evaluation 的重复追迹问题。
    
2.  B 负责 profiling、基准数据采集、缓存设计、重构后的可维护性把控。
    
3.  C 负责在非当前项目样例上复验优化后的收益和稳定性，避免优化只对单一系统有效。
    

这一步尤其需要避免“只有单一系统加速了，但泛化性能退化”的情况。

## 5.7 阶段 6：图像仿真扩展

目标：

在 tracing 和 evaluation 稳定后，加入 PSF、MTF 和图像形成相关能力。

建议分工：

1.  C 主导需求定义，因为其跨项目视角更适合决定图像仿真接口应如何泛化。
    
2.  A 审核图像仿真与当前 optical model 的一致性。
    
3.  B 负责接口落地、模块组织和测试接入。
    

## 6. 三个人最适合承担的具体产出

为了避免分工过虚，建议直接把每个人的产出物说清楚。

## 6.1 A 的产出物

建议 A 交付：

1.  tracing/evaluation 语义说明
    
2.  必须保持一致的数值行为清单
    
3.  关键 benchmark case 的光学解释说明
    
4.  性能热点判断和优化可行性说明
    

不建议要求 A 主导的产出物：

*   完整测试框架
    
*   包结构重构方案
    
*   自动化 benchmark 平台
    

## 6.2 B 的产出物

建议 B 交付：

1.  optics\_core 模块结构方案
    
2.  接口定义文档
    
3.  regression/contract/benchmark 测试框架
    
4.  第一次接口剥离的适配层
    
5.  benchmark 汇总报告和迭代计划
    

## 6.3 C 的产出物

建议 C 交付：

1.  跨项目泛化约束清单
    
2.  独立 benchmark case 设计
    
3.  Zemax API / Optiland 对标方案
    
4.  图像仿真阶段的未来需求草案
    

## 7. Zemax API 和 Optiland 能否用于 benchmark

结论：能，而且建议都用，但用途不同，不要混为一种 benchmark。

## 7.1 Zemax API 的建议定位

Zemax API 更适合作为“外部权威参考 benchmark”。

原因：

1.  团队已经相对熟悉 ZOS-API。
    
2.  当前仓库已经有 json2zmx.py、excel2zmx.py 和 PythonStandaloneApplication.py，可作为现有桥接基础。
    
3.  对于 spot、MTF、chief ray、像高、CRA、部分系统参数，Zemax 可以作为非常强的对照来源。
    

建议 Zemax benchmark 用于：

1.  选取 3 到 5 个代表性系统做外部对标。
    
2.  对比 EFL、BFL、像高、spot RMS、CRA、MTF 等关键指标。
    
3.  检查新基础库在重构后是否仍然与工业工具近似一致。
    

注意事项：

1.  不能要求所有指标逐点完全一致，因为 stop 定义、材料模型、非球面参数和求解设置可能不完全同构。
    
2.  Zemax 更适合作为参考真值之一，而不是唯一真值。
    
3.  Benchmark case 数量不宜太多，否则维护成本会很高。
    

## 7.2 Optiland 的建议定位

Optiland 更适合作为“开源参考实现和接口设计 benchmark”。

适合它的用途包括：

1.  用于对照一个更通用的开源 ray tracing library 如何组织 system、ray bundle、trace result。
    
2.  用于简单系统上的功能性 smoke test。
    
3.  用于评估 optics\_core 接口是否过度耦合当前项目。
    

不建议把 Optiland 作为第一权威 benchmark 的原因是：

1.  它的材料模型、非球面支持、求值路径和当前项目不一定完全一致。
    
2.  对复杂系统的数值结果不一定能直接作为最终 acceptance criteria。
    
3.  它更适合做“结构参考”和“轻量功能对照”，不太适合直接替代 Zemax 的对标价值。
    

## 7.3 建议的 benchmark 三层结构

最推荐的 benchmark 体系不是二选一，而是三层并用：

1.  内部回归 benchmark 以当前 DiffOptics 实现为基线，保证重构前后行为不漂移。
    
2.  Zemax benchmark 用于验证关键 optical 指标与工业工具是否对齐。
    
3.  Optiland benchmark 用于验证接口设计是否通用、简单系统功能是否合理。
    

这样三层各自负责：

*   第一层防回归
    
*   第二层防偏物理语义
    
*   第三层防架构封闭
    

## 8. benchmark 构建建议由谁负责

建议拆成下面的 owner 关系：

1.  B 负责 benchmark 框架、数据记录格式、自动运行和结果汇总。
    
2.  C 负责设计 Zemax 和 Optiland 的对标 case 与对比维度。
    
3.  A 负责解释 benchmark 不一致的原因，并决定是修实现、调容差还是接受模型差异。
    

这样可以避免：

*   B 写 benchmark 但不知道指标为什么偏
    
*   A 看数值但没有统一框架沉淀结果
    
*   C 熟悉外部工具却没有进入核心判断链
    

## 9. 建议的协作节奏

建议采用轻量但固定的节奏，不建议完全自由协作。

建议每周至少有两类同步：

1.  设计同步 由 B 主持，A 和 C 参加，讨论接口、迁移策略和 benchmark 设计。
    
2.  数值同步 由 A 主持，B 和 C 参加，集中看回归差异、benchmark 差异和性能数据。
    

每次同步最好只看三类材料：

1.  当前文档和接口变更
    
2.  测试结果摘要
    
3.  一个明确待决策问题
    

不要把同步会变成大段代码 walkthrough，那样效率会很低。

## 10. 初步里程碑分配

建议按下面方式认领里程碑。

| 里程碑 | 内容 | 主负责人 |
| --- | --- | --- |
| M1 | optics\_core 边界和接口定义完成 | B |
| M2 | 基线测试与 benchmark 框架完成 | B |
| M3 | tracing 与 evaluation 第一次剥离完成 | B |
| M4 | Zemax / Optiland benchmark 建立完成 | C |
| M5 | 第一轮性能优化完成 | A |
| M6 | imaging 扩展设计完成 | C |

这里需要特别说明：

*   主负责人不代表单独完成
    
*   主负责人代表对最终结果负责
    
*   A、B、C 仍然都需要在各阶段给出专业判断
    

## 11. 最推荐的执行方式

如果只给一句最务实的建议，那就是：

1.  由 B 主导整个工程化重构
    
2.  由 A 把住 tracing 和 evaluation 的算法正确性
    
3.  由 C 负责把外部 benchmark 和跨项目泛化约束带进来
    

这个组合最符合三个人当前的能力结构，也最能降低风险。

如果反过来做，比如让 A 主导工程重构、让 B 只做支持、让 C 晚些再介入，那么高概率会出现两个问题：

1.  初版能跑，但接口和测试体系不稳
    
2.  后面才发现库设计仍然过度绑定当前项目
    

因此推荐直接从一开始就按“三角分工”推进，而不是先让某个人单核推动到后期再补位。
